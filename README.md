# HR Policy Assistant

A lightweight retrieval-augmented generation (RAG) application that answers questions about an HR policy handbook using a vector database and an LLM. The project is built in Python and uses LangChain, FAISS, Groq, and Jina embeddings.

## Project overview

This application reads policy text from a local document, splits it into smaller chunks, converts those chunks into embeddings, stores them in a FAISS index, and retrieves the most relevant policy passages when a user asks a question. The LLM then uses those retrieved passages to answer the query in a grounded, policy-aware way.

The main user-facing entry points are:

- [app.py](app.py) — Streamlit web interface
- [main.py](main.py) — command-line demo
- [hr_assistant/pipeline.py](hr_assistant/pipeline.py) — orchestration layer

## Configuration and environment

All runtime settings are centralized in [hr_assistant/config.py](hr_assistant/config.py).

Required environment variables:

- GROQ_API_KEY
- JINA_API_KEY

The app loads them from a local .env file using python-dotenv.

Example:

```env
GROQ_API_KEY=your_groq_key
JINA_API_KEY=your_jina_key
```

Key configuration values:

- LLM_MODEL_NAME = openai/gpt-oss-120b
- EMBEDDING_MODEL_NAME = jina-embeddings-v2-base-en
- CHUNK_SIZE = 500
- CHUNK_OVERLAP = 50
- TOP_K_RESULT = 3
- DATA_FILE_PATH = data/hr_policy.txt
- vector_STORE_PATH = data/faiss_index

## How the project works

### 1. Load the document
The app reads the HR policy handbook from [data/hr_policy.txt](data/hr_policy.txt) using a LangChain text loader.

### 2. Split into chunks
The text is divided into overlapping chunks using a recursive character splitter. This helps preserve context while keeping each chunk small enough for embedding and retrieval.

### 3. Create embeddings
Each chunk is converted into a vector using Jina embeddings.

### 4. Build the vector store
The vectors are stored in a FAISS index so the app can search semantically for relevant policy text later.

### 5. Retrieve relevant data
A retriever is created from the FAISS store and returns the top-k relevant chunks for a user question.

### 6. Expose retrieval as a tool
The app wraps retrieval in a LangChain tool called search_hr_policy. This allows the LLM to decide when to query policy facts before answering.

### 7. Create the agent
The LangChain agent combines the Groq model and the policy search tool under a system prompt that says: use the tool to find evidence before answering, and do not guess when the answer is missing.

### 8. Answer the question
The user asks a question in the UI or CLI. The agent invokes the retriever tool, reads matching passages, and generates a response grounded in the policy content.

## Main application flow

### CLI flow
The command-line path begins in [main.py](main.py):

1. Build the HR assistant
2. Ask a few demo questions
3. Print each answer to the terminal

### Streamlit flow
The web flow begins in [app.py](app.py):

1. Load the assistant using a cached resource
2. Show a chat interface
3. Store conversation history in session state
4. Query the policy-aware agent for each new question
5. Display the answer and keep chat history

## Key modules and responsibilities

### [hr_assistant/config.py](hr_assistant/config.py)
Responsible for all global constants and startup validation. It loads environment variables, declares model names, chunking parameters, and retrieval settings, and ensures the required API keys exist before the assistant runs.

### [hr_assistant/document_loader.py](hr_assistant/document_loader.py)
Loads the raw text file as LangChain Document objects.

### [hr_assistant/splitter.py](hr_assistant/splitter.py)
Breaks the policy text into smaller chunks with overlap.

### [hr_assistant/embeddings.py](hr_assistant/embeddings.py)
Initializes the Jina embedding model used by FAISS.

### [hr_assistant/vector_store.py](hr_assistant/vector_store.py)
Builds, saves, loads, and queries the FAISS vector database.

### [hr_assistant/llm.py](hr_assistant/llm.py)
Initializes the Groq chat model used by the AI agent.

### [hr_assistant/tools.py](hr_assistant/tools.py)
Creates the search tool. This tool is critical because it is the bridge between retrieval and LLM reasoning.

### [hr_assistant/agent.py](hr_assistant/agent.py)
Creates the LangChain agent that binds the LLM and tool chain together.

### [hr_assistant/pipeline.py](hr_assistant/pipeline.py)
This is the orchestrator. It is the central entry point for building the assistant and asking questions.

## Setup instructions

1. Create and activate a virtual environment.
2. Install dependencies.
3. Add your API keys to a .env file.
4. Run the assistant.

Example:

```bash
python -m venv ragassistant
ragassistant\Scripts\activate
pip install -r requirement.txt
```

Then start the web app:

```bash
streamlit run app.py
```

Or run the CLI demo:

```bash
python main.py
```

## Current behavior and design notes

This project is intentionally simple and practical:

- It uses a single local HR policy document instead of a full database.
- It caches the FAISS index to avoid rebuilding it each time.
- It keeps the agent grounded by requiring a retrieval step before answering.
- It is designed for a specific domain, which makes it fast to understand and easy to extend.

## Strengths

- Clear modular architecture
- Easy to trace data flow between file loading, embedding, retrieval, and answer generation
- Convenient for internal HR policy queries
- Reusable components for other domain-specific document assistants

## Limitations

- The app only supports the current local HR policy file.
- It does not yet include multi-document ingestion or a more advanced document management system.
- It assumes the source material is mostly structured text without heavy PDF parsing or OCR.
- It depends on external API credentials from Groq and Jina.

## Suggested next improvements

- Add PDF and DOCX support
- Add a proper front-end dashboard with authentication
- Add caching and monitoring for model calls
- Support multi-file policy documents and automatic indexing
- Add conversation memory and follow-up question handling
- Add unit tests and evaluation checks for answer quality

## Summary

This project is a small but complete RAG application for HR policy Q&A. It follows a standard retrieval-augmented pipeline: document -> chunk -> embed -> index -> retrieve -> answer with an LLM. The design is modular, easy to follow, and a strong foundation for expanding into a broader organizational knowledge assistant.
